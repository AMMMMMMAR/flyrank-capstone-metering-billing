# Build Log

## Stage 0
- Restarted the capstone from scratch with Claude as a mentor, because I
  wanted to understand every line of my own code.
- An earlier attempt generated by another AI agent was discarded.
- Claude wrote the Stage 0 code; I read and ran it.

## Stage 1
- Claude wrote the models, config, and seed script; I read them and ran them.
- Decided: SQLite first, one usage event per call, UTC calendar month,
  integer micro-dollars, API keys stored only as SHA-256 hashes.

## Stage 2
- Claude wrote the auth dependency and the /me endpoint; I read them and ran them.
- Decided: tenants identify themselves with a secret X-API-Key header.
  Only the SHA-256 hash is stored. X-Tenant-ID was rejected because anyone can fake it.

## Stage 3
- Claude wrote POST /generate, the metering service, and the validation; I read and ran them.
- Decided: the server sets calls=1, the tenant comes only from the API key,
  Idempotency-Key header is required, extra fields are rejected.
- A repeated key returns 409 for now. Stage 5 will return the original response instead.

## Stage 4
- Claude wrote the quota service, the locking in the metering service, and the check script;
  I read them and ran them.
- Decided: rule is used + requested <= limit, UTC calendar month, 429 over quota,
  402 only for past_due, nothing is saved for a rejected request.
- Known limit: the Python lock only protects one server process. PostgreSQL row locks fix that.

## Stage 5
- Claude wrote the idempotency table, the new metering service, and the proof script;
  I read them and ran them.
- Decided: check the key BEFORE the quota, so a retry after a successful call gets the
  original answer. Only successful (200) responses are saved.
- Corrected an earlier plan: no in_progress row and no polling. One transaction plus the
  tenant lock is simpler: a concurrent duplicate just waits, then replays.
- Known limit: records are not deleted yet. A cleanup job comes in Stage 8.

## Stage 6
- Claude wrote the pricing service, GET /usage and the proof script; I read them and ran them.
- Decided: demo prices pinned in config, reasoning billed as output, round up once per
  bucket on the monthly totals, calls priced at 100 micro-dollars each.
- Corrected the earlier plan: money is called micro-dollars (not micro-cents), and the cost is
  not stored on each event, it is calculated from the monthly totals.

## Stage 7
- Claude wrote the checkout service, the webhook handler and the proof script;
  I read them and ran them.
- Decided: the tenant id is written into client_reference_id and subscription metadata;
  signatures are checked on the raw body; the event id and plan change are saved in one
  transaction; older events are ignored (out of order); unknown events return 200.
- I did not run the unverified "irm ... | iex" install script. I installed the Stripe CLI with
  winget, from Stripe's documented install options.

## Stage 8
- Claude wrote the cleanup job, the retry/alert runner, the lifespan wiring and the proof script;
  I read them and ran them.
- Decided: a small thread-based scheduler (no new library), 3 attempts with 1s/2s backoff,
  alert = CRITICAL log + job_alerts row, delete in batches.
- Claude found a bug in its own Stage 5 code: flush() was outside the try block, so an expired
  key would have caused a 500. Fixed in metering.py and covered by check_cleanup.py.

## Stage 9
- Claude wrote the Alembic setup, the baseline migration, the new seed script and the proof script;
  I read them and ran them.
- Decided: one baseline migration written by hand and checked against models.py by the proof script
  (no differences); stamp the existing database instead of rebuilding it; SQLite stays the database.
- Honest limit: I only ran the migrations on SQLite. Postgres would need its own driver and a test run.
